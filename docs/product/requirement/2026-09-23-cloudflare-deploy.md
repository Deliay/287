# 产品需求文档：Cloudflare 部署支持

- 主题名：`cloudflare-deploy`
- 创建日期：2026-09-23
- 状态：待评审

## 1. 背景与目标

当前站点（287 粉丝站）是一个基于 Next.js 16 的纯静态单页应用，只能在本地通过 `next dev` / `next start` 运行，缺乏面向公网的低成本、可持续的部署方案。

本期目标：引入 [Wrangler](https://developers.cloudflare.com/workers/wrangler/)（Cloudflare 官方 CLI），使站点可以一键构建并部署到 Cloudflare，获得全球 CDN 分发能力，且个人/小团队使用成本趋近于零。

## 2. 用户场景

- **维护者（开发者）发布站点**：在本地执行一条命令，完成构建并部署到 Cloudflare，随后可通过分配的域名访问站点。
- **维护者部署前预览**：在本地以接近 Cloudflare 运行时环境的方式预览构建产物，确认无误后再正式发布。
- **访客访问站点**：通过 Cloudflare 分配的 `*.workers.dev` 域名（或后续绑定的自定义域名）访问站点首页，页面、图片、样式加载正常。

## 3. 功能需求

1. 作为维护者，我希望项目内集成 Wrangler 作为开发依赖，以便无需全局安装即可使用部署工具链。
2. 作为维护者，我希望项目提供 `pnpm run deploy` 之类的脚本，一条命令完成「构建 → 部署到 Cloudflare」。
3. 作为维护者，我希望项目提供本地预览脚本（如 `pnpm run preview`），可以在部署前以 Cloudflare 静态资源服务的方式验证产物。
4. 作为维护者，我希望部署配置（站点名、静态资源目录等）以配置文件形式纳入版本管理（如 `wrangler.toml` / `wrangler.jsonc`），以便部署行为可复现、可审查。
5. 作为维护者，我希望部署后站点功能与本地 `next build` 产物一致：首页、成员区块、立绘图片、平滑滚动等行为无回归。

## 4. 验收标准

1. `pnpm install` 后，`pnpm exec wrangler --version` 可正常输出版本号，无需全局安装。
2. 执行部署脚本后，命令输出部署成功的 Cloudflare 地址（`*.workers.dev`），且该地址可访问。
3. 访问部署后的站点：首页正常渲染；Hero 立绘墙与成员区块图片正常加载；无 404 资源（`public/` 下静态资源均可访问）。
4. 本地预览脚本启动后，可在浏览器访问与部署产物一致的页面。
5. 部署配置文件纳入 git 管理，且不包含任何密钥（认证依赖环境变量或 `wrangler login`，凭据不入库）。
6. 现有开发流程不受破坏：`pnpm run dev`、`pnpm run build`、`pnpm test`、`pnpm run lint` 全部正常工作。
7. 新增针对部署配置的测试（如校验配置文件与构建产物目录一致性）并通过。

## 5. 非功能需求

- **成本**：使用 Cloudflare 免费套餐额度内完成部署，不引入付费依赖。
- **兼容性**：不改变现有页面在主流桌面与移动浏览器上的行为。
- **安全**：Cloudflare 账号凭据（API Token / OAuth）不得写入仓库；部署配置文件中不出现任何 secret。
- **性能**：部署后静态资源经 Cloudflare CDN 分发，国内/海外访问延迟不劣于直接回源。

## 6. 范围边界

本期**不做**：

- 不绑定自定义域名，不配置 DNS。
- 不接入 CI/CD 自动部署（GitHub Actions 等），仅提供本地手动部署能力。
- 不引入 Cloudflare Workers 动态计算逻辑（无 API 路由、无服务端渲染需求，站点保持纯静态）。
- 不做访问统计、缓存策略精细化等运营向配置。
